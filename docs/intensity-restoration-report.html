1. 원인 — 변환 파이프라인 어디서 intensity가 사라졌나

rosbag과 중간 산출물(raw .bin)에는 intensity가 살아 있고, 최종 pcd에서만 사라짐 → raw .bin → .pcd 변환 단계가 소실 지점.

단계증거intensity
rosbag메시지 정의에 intensity 필드 존재 (Hesai/Velodyne PointCloud2)있음
raw .bin355,504B ÷ 16 = 22,219pt 정수 분할, 4번째 열 0~255 실측있음
dataset .pcd헤더 FIELDS x y z / SIZE 4 4 4 / TYPE F F F없음
재패키징 스크립트 11개a2z.py, data_ver2.py, last.py 등 — 전부 shutil.copy로 pcd 그대로 이동 (무관)-

실제 bin→pcd 변환 스크립트는 탐색 범위(~/24_04, ~/project_ws, 데이터셋 폴더 등)에서 발견되지 않았다 (삭제 또는 다른 머신에서 실행된 것으로 추정). 같은 시기에 작성된 /home/a/24_04/auto_calib_saver.py가 pc2.read_points(..., field_names=("x","y","z"))로 xyz만 추출하는 동일한 실수 패턴을 보여준다. open3d write_point_cloud 사용 가능성도 높다 — open3d PointCloud 자료구조에는 intensity 속성이 없어 조용히 버려진다.

2. 복원 방법 — 좌표 보존 intensity 이식 실행 완료

GT 어노테이션 63,463개가 기존 pcd 좌표 기준이므로, 재변환 대신 기존 pcd의 xyz 바이트를 그대로 두고 intensity 컬럼만 이식하는 방식을 사용.

  1. 매핑 규칙 (사전 검증): 파일명 z{NN}-{타임스탬프}_{프레임}.pcd → raw 씬 {NN}_{타임스탬프}의 {프레임}.bin. 센서는 디렉토리명으로 매핑 (point_cloud_16·lidar_point_cloud_16→velodyne, lidar_point_cloud_0·_64→hesai64)
  2. 사전 게이트: 샘플 프레임에서 pcd와 bin의 좌표가 KDTree 거리 0으로 100.000% 일치, 포인트 수·순서까지 동일함을 확인 (velodyne 22,219pt, hesai 220,166pt)
  3. 프레임별 안전장치: 포인트 수 또는 xyz 배열이 bin과 정확히 일치하지 않으면 건드리지 않고 스킵·로그 (실제 발생 0건)
  4. 원자적 쓰기: .tmp 작성 후 rename — 중단돼도 파일 손상 없음. 멱등 설계 (이미 복원된 파일은 자동 스킵)
  5. 가역성: 새 pcd에서 intensity 컬럼만 제거하면 원본과 바이트 단위로 동일하게 되돌릴 수 있음 (헤더 템플릿 동일 확인)

도구: training/restore_intensity.py (드라이런 → 적용, 워커 수·데이터셋·샘플 수 옵션)

4.1 현재 저장 구조 (조사 결과)

항목값

4.2 권장 범위: 어노테이션된 16개 데이터셋만

  • 전체 57,512개 교체는 로컬 디스크 용량상 불가 (MinIO 볼륨이 로컬 NVMe에 있고 여유 82GB, 필요 증가량 ~66GB 초과)
  • 어노테이션된 16개 데이터셋(ds id 7,8,9,10,11,14,26,28,33,37,38,39,40,41,42,45) = 원본 18,184개 / 25.6 GiB → 증가량 원본 +8.5GiB, binary +~17GiB로 수용 가능
  • 주요 대상: Zenix_Night_1(2,612), Zenix_Day_1(1,143), Zenix_Night_14(898), Zenix_Day_2(789) 등

4.3 실행 절차 (실행 승인 시)

  1. 백업: docker exec ... mysqldump xtreme1 file > file_backup.sql + 교체 대상 객체 목록/크기 저장
  2. 원본 교체: 대상 데이터셋의 file 레코드(path, name)를 SELECT → 디스크의 복원된 pcd를 같은 키로 mc cp 덮어쓰기 (자격증명: compose의 admin/1tQB970y, 버킷 xtreme1, 네트워크 xtreme1_gpu_roboticslab_default). 파일명+크기(기존 size = 디스크 원본 크기였음) 일치 검증 후 교체
  3. DB 갱신: 원본 레코드 UPDATE file SET size = {새 크기} (새 크기 = 기존 size × 4/3 + 헤더 차이)
  4. 파생 binary 재생성: 프레임당 pcd-tools convert_render 호출 (원본 GET presigned + binary/render PUT presigned) → binary-*가 x y z i로 재생성, 응답의 binaryPcdSize·imageSize·pointCloudRange로 파생 file 레코드 갱신. 18,184프레임 × 1~2초 ≈ 5~10시간 (render 포함 재생성; render만 따로 건너뛸 수는 없음 — API가 쌍으로 생성)
  5. 검증: ① binary 객체 헤더에 x y z i 확인 ② SELECT COUNT(*) FROM data_annotation_object 전후 동일 ③ pc-tool로 프레임 1개 열기 ④ 모델 런 1회 (이제 intensity가 실제값으로 모델에 전달됨)

4.5 리스크와 참고

  • 2~4단계 사이 중단되면 일부 프레임은 원본(intensity有)·binary(intensity無) 불일치 상태가 되지만, 뷰어·모델 모두 동작엔 문제 없음 (binary 우선 로드) — 재실행으로 수렴
  • 업로드 안 된 나머지 디스크 데이터는 이미 복원됐으므로, 향후 새 데이터셋 업로드는 자동으로 intensity 포함
  • 파인튜닝 파이프라인(training/)은 디스크 pcd를 읽으므로 이번 복원만으로 즉시 intensity 학습 가능 — MinIO 교체는 Xtreme1 안에서의 모델 런/시각화용

5. 되돌리기

  • 디스크 복원분: 새 pcd에서 4번째(intensity) 컬럼 제거 + 기존 헤더 템플릿으로 재작성하면 원본과 바이트 동일 (raw .bin이 원천 데이터로 NAS에 보존돼 있어 언제든 재생 가능)
  • MinIO/DB: 아직 아무것도 변경하지 않음 — 되돌릴 것 없음. 실행하게 되면 1단계 백업(file_backup.sql + 객체 목록)이 복원 수단
