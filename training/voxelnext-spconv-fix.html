에러무엇이 터졌나

VoxelNeXt를 nuScenes 사전학습 가중치로 파인튜닝하려고 --pretrained_model을 줬더니, 학습 시작 직전 사전학습 ckpt를 모델에 로드하는 단계에서 즉시 죽었습니다. (CenterPoint 파인튜닝은 동일 환경·동일 spconv에서 멀쩡히 됐음)

원인왜 터졌나

OpenPCDet의 _load_state_dict는 spconv(희소 합성곱) 가중치를 로드할 때 버전 간 shape 차이를 자동 보정하는 로직이 있습니다. 사전학습과 현재 모델의 spconv 가중치 shape가 다르면:

for key, val in pretrained.items():
    if key in spconv_keys and state_dict[key].shape != val.shape:   # shape 불일치
        val_native = val.transpose(-1,-2)        # ① 전치로 맞춰보기
        if val_native.shape == state_dict[key].shape: val = val_native
        else:
            assert val.shape.__len__() == 5, 'currently only spconv 3D is supported'  # ← 여기서 죽음
            val_implicit = val.permute(4,0,1,2,3)  # ② 차원 재배열로 맞춰보기
    if state_dict[key].shape == val.shape:        # ③ 그래도 맞으면 로드, 아니면 스킵
        update_model_state[key] = val

핵심: 파인튜닝은 클래스가 다릅니다 (nuScenes 10클래스 → zenix 6클래스, 헤드 그룹 구조도 다름, 입력피처 5→4). 그래서 검출 헤드의 spconv 가중치가 사전학습과 shape가 다릅니다. 원래 의도는 "strict=False니까 안 맞는 키는 그냥 스킵(헤드는 새로 초기화)"인데, ①②로도 못 맞추는 비-5D spconv 키에서 하드 assert가 스킵을 막고 프로세스를 죽여버립니다.

왜 CenterPoint는 됐나아키텍처 차이

CenterPoint (성공)VoxelNeXt (실패)

즉 같은 코드라도, VoxelNeXt는 "완전 희소(fully sparse)" 구조라 헤드까지 spconv 키여서 이 보정 분기를 타고 assert에 걸린 것입니다. CenterPoint 헤드는 일반 conv라 애초에 이 분기를 안 탑니다.

해결패치 — assert를 조건부 스킵으로

학습측 OpenPCDet pcdet/models/detectors/detector3d_template.py의 하드 assert를 조건문으로 바꿔, 보정 불가한 spconv 키는 그냥 흘려보내고 ③의 shape 일치 검사에서 자연스럽게 스킵되게 했습니다 (= 헤드 재초기화, 파인튜닝의 정상 동작).

변경 전: 비-5D spconv 키 만나면 죽음.   변경 후: 비-5D & 보정 불가 키는 스킵 → 나머지 백본 가중치는 정상 이전, 헤드만 재초기화.

안전성이 패치가 안전한 이유

  • 학습측만 수정: 패치는 학습 서버의 OpenPCDet에만 적용. 서빙 이미지는 무관 — 서빙은 내가 학습한 ckpt를 같은 cfg로 로드하므로 shape가 100% 일치 → 보정 분기 자체를 안 탐.
  • 의도된 동작과 일치: strict=False 로드의 본래 목적이 "안 맞는 키는 스킵". 패치는 그 목적을 spconv 키에도 적용했을 뿐, 새 동작을 만들지 않음.
  • 가중치 이전은 보존: shape가 맞는 백본(VoxelResBackBone8xVoxelNeXt) 가중치는 그대로 로드됨. 입력 첫 레이어(4≠5)와 클래스 헤드만 재초기화 — 파인튜닝의 정상 절차.
  • 결과로 검증됨: 패치 후 재실행 시 사전학습 로드 통과, Loss 10.8 → 6.2로 정상 수렴, GPU 정상 사용.
